# JG-029 Error monitoring and support references

Implementation and local acceptance completed on 2026-11-16 (Asia/Shanghai). Implementation revision [ab108de](https://github.com/Enfoirer/jobgenie/commit/ab108deaaf5d1e3b9743bd08b2e21d1107d28e6a).

## Requirements and key decisions

Add server, browser and native API diagnostics with a user-visible reference that administrators can look up. Cover unexpected HTTP failures, web uncaught errors/rejections and render recovery, native network failures and invalid response types. Preserve successful requests, expected business failures and framework control flow. Read the [coverage and operating rules](../../error-monitoring-acceptance.md).

Use an explicit metadata allowlist. Passwords, tokens, headers, cookies, email bodies, arbitrary exception messages, full stacks, queries and request/response bodies are excluded from application-owned incident records. Known source positions are validated against a repository filename catalog. Client reporting requires authentication, same-origin validation, bounded packets and rate limits. Administrator page/API reads check the live role and filter reference, platform, exact version and inclusive UTC dates.

Selected defaults are 30-day retention and UTC-calendar-minute grouping. Accepted matching reports share a reference and increment its report count. Browser/native clients suppress repeated packets for a short interval. A count measures accepted reports. Database persistence has a two-second response budget with safe structured-log fallback. A late write may finish. Client transport is best effort and depends on authentication/connectivity. Logout clears native references and rejects stale replies.
