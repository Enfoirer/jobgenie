# Repository workflow

User preferences for this repository:

- After completing and validating an authorized feature or fix, create a Git commit and push it to the GitHub remote without waiting for a separate request. The user expects “commit” to include synchronization to GitHub. Write commit subjects and bodies in English. Stage only changes belonging to the task, use the configured branch/remote, and verify the remote commit SHA before reporting completion. Honor any explicit request to keep a particular change local.
- Update `docs/progress/project-progress.xlsx` whenever work is completed or its status changes. Keep task IDs stable, update the Gantt dates/status, and append to the existing Update Log sheet rather than overwriting history.
- Keep `docs/progress/README.md` current with the update date, evidence links, and relevant remaining acceptance boundaries. Use the existing `docs/progress/project-progress.xlsx` as the only maintained workbook. Do not create or maintain additional workbook copies in outputs, archives, or new folders.
- Record actual test results and dates. Distinguish implementation, local acceptance, production deployment, and signed-device/TestFlight acceptance. Do not mark deployment or real-provider verification complete merely because local tests passed.
- Include progress updates with the delivery. When a fixed commit link cannot refer to the commit containing the workbook itself, make a subsequent progress-record commit that links to the completed implementation commit.
- GitHub pushes may trigger the repository's existing Vercel integration; distinguish a successful push from a successful deployment in reports. Additional deployment actions and TestFlight distribution still follow the user's authorization.
- After every development delivery, update all four evidence categories under `docs/progress/`, linked by task ID and implementation commit: requirements/key decisions, actual test/build logs, screenshots/recordings or API examples, and deployment observations. Follow `docs/progress/recording-guidelines.md` and its template. Save the records with the workbook update and push them to GitHub. Record missing or inapplicable evidence explicitly; do not invent an old log, screenshot, timestamp, test result or deployment.
- Public test/build logs and visual evidence must be reviewed and sanitized before committing. Keep untouched originals and personal/business/financial/school documents in the private parent-workspace `records/jobgenie/` directory, outside Git. Do not publish credentials, production data, home paths or personal documents. Never infer work hours, customer activity or revenue from commits. Label retrospective summaries with the actual preparation date. Completed milestones do not mean the product as a whole is complete.
- Maintain progress/evidence documents, acceptance records, index descriptions, workbook text and new record filenames in English. Keep the original workbook as the only maintained tracker, now translated and renamed in place. Preserve the bilingual Chinese/English iOS product. Do not rewrite original-language raw test output, historical Git commits or fixed source links; record the translation date and preserve provenance.
